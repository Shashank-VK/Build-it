# Atlassian — product engineering case study (design system + the 2022 outage)

Workstream: expansion-companies · Researched 2026-10-10 · Read-only research; no installation, ranking, or recommendation.

## Scope notes
Atlassian earns its place twice: the **Atlassian Design System (ADS)** powering Jira/Confluence/Trello with token-driven theming (including the notable "Teaching AI to speak our design language" program — ADS MCP + measured agent accuracy/speed/token-cost), and the **April 2022 cloud outage** — a maintenance script permanently deleted ~400–775 customers' sites, with a 7,500-word public post-incident review. The outage is the stronger case; the design system is the steadier one.

## 1. Forensic reconstruction — how the machine actually works

### ADS: tokens as the theming substrate
- Claim: The Atlassian Design System provides tokens, components, and patterns consumed across Jira, Confluence, Trello, and more; **dark mode ships via the token layer** (swap token values, not component code) — the same architectural move as Carbon. Label: **Corroborated** — aidesigner.ai overview; atextit AI-design-resources research notes. Confidence: medium-high.
- Claim: **"Teaching AI to speak our design language"**: Atlassian exposed ADS via **MCP (Model Context Protocol) + agent skills**, and — unusually — *measured* the results: agent accuracy, speed, and token-cost when generating ADS-conformant UI. Label: **Corroborated** (aittextit research notes; aidesigner.ai). Confidence: medium (program described in secondary sources; the actual metrics not fetched as primary). The forensic significance: Atlassian treats AI-assisted UI generation as an *evaluated* capability, not a demo — accuracy/speed/cost is the right metric triple, and almost nobody else publishes it.

### The outage machine: what the postmortem revealed about the platform
- Claim: Atlassian's cloud runs thousands of internal microservices with per-customer site provisioning; a **maintenance script** (deleting legacy data from a deprecated Insights app merged into Jira Service Management) was run with the **wrong execution mode and wrong ID list** — it received entire cloud-site IDs instead of app IDs and ran in **permanent-deletion mode** instead of recoverable soft-delete. ~400 customers' sites (later revised to **775**) were deleted: Jira, Confluence, JSM, Opsgenie, Access. Label: **Verified** — Atlassian's 7,500-word post-incident review (Apr 29, 2022) via techtarget's reporting; completestatus. Confidence: high.
- Claim: The script **wasn't caught in peer review**; the deletion executed as legitimate API calls, so monitoring flagged it as normal activity; the deletion even removed **contact info for affected customers**, hobbling Atlassian's own incident communications (customers couldn't open support tickets normally). Label: **Verified** (post-incident review via techtarget). This is the detail that elevates the case: the blast radius included the *communications path*.

## 2. Postmortem record — the two weeks, dissected
- **Timeline (Apr 5–19, 2022):** script deletes sites → detection → restoration begins → only ~35% restored after a week → all sites restored by ~Apr 19 (two weeks). **No data loss** for restored customers (backups intact) — but restoration was slow, largely manual per-site rebuilds: infrastructure re-provisioning, data restore, dependency validation, without rolling back unaffected customers sharing the infrastructure. Label: **Corroborated** — techtarget (Apr 12, May 3); completestatus; theregister.
- **What broke (layer by layer):** (1) script review — improperly formed script passed peer review; (2) execution modes — permanent-delete was a runnable option on production data with no soft-delete default; (3) blast-radius controls — one script could address entire customer sites; (4) monitoring — legitimate-API-call deletions looked normal; (5) **recovery architecture** — backups existed but covered the data layer, not configs/integrations; per-site manual rebuilds took two weeks; (6) communications — slow, generic, "only a small percentage" framing; deleted contact info compounded it. Label: **Corroborated** (post-incident review).
- **What changed:** Atlassian committed to **soft deletes** for similar operations, more extensive disaster-recovery exercises, and better customer outreach. Label: **Corroborated** (techtarget, May 2022). Whether the DR exercises actually run on schedule is **Unknown** — no follow-up audit found.

## 3. Narrative audit — dismantling with receipts
- **"We maintain extensive backup and recovery systems" vs. two weeks.** Atlassian's early statement leaned on backups — technically true, practically misleading. The receipts: backups covered *data*, not *the site* (configs, integrations, provisioning) — and recovery speed, not backup existence, was the SLA that mattered. The dismantling: **backups are not recovery**. Any DR claim should quote *restoration time for a full customer environment*, measured by exercise, not *backup coverage*. Atlassian's own review effectively concedes this. Label: **Inferred** (audit synthesis) on **Verified** review facts.
- **The peer-review failure is the scariest line.** A script that can permanently delete customer sites passed peer review with wrong IDs and wrong mode. The audit: review processes fail exactly when the change looks routine ("cleanup script") — the boring changes get the least scrutiny and carry production credentials. The fix isn't "review harder"; it's **make dangerous operations structurally safe** (soft-delete defaults, blast-radius limits, dry-run requirements) so review isn't the only control. Label: **Inferred** on **Verified** facts.
- **"Only a small percentage" — the comms postmortem.** Atlassian's early communications were widely criticized as slow and minimizing; completestatus's piece ("Two Weeks of Downtime and What Not to Say") is essentially a comms postmortem. The audit: for the 775 affected customers the percentage was 100% — aggregate framing is experienced as dismissal. Status communication should be written for the affected, not the unaffected. Label: **Inferred** on **Corroborated** criticism.
- **ADS + AI measurement: credit where due, with one caveat.** The "teaching AI our design language" program with measured accuracy/speed/token-cost is genuinely ahead of the industry (most design-system AI efforts are demos). The caveat: the metrics are Atlassian-reported via secondary sources — the primary evaluation methodology wasn't fetched. Trust but verify before citing the numbers. Label: **Corroborated** (program) / **Unknown** (exact figures).

## Transferable lessons
1. **Backups are not recovery.** Quote full-environment restoration time, proven by exercise. Data-layer backups without config/integration recovery = two-week manual rebuilds.
2. **Internal tools are production systems.** Cleanup scripts need the same scrutiny as deploys: soft-delete defaults, blast-radius limits, dry-run modes, and review calibrated to *privilege*, not *boringness*.
3. **Permissions define blast radius.** A maintenance script should never hold credentials capable of deleting entire customer sites.
4. **Monitoring must catch legitimate-but-wrong API calls.** Anomaly detection on deletion *volume/scope*, not just auth failures.
5. **Write status updates for the affected.** "Small percentage" framing is heard as minimization. Lead with what's being done for the people down.
6. **Measure AI-assisted UI generation** (accuracy/speed/token-cost) instead of demoing it — Atlassian's metric triple is the template.
