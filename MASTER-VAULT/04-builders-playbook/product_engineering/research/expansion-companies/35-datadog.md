# Datadog — product engineering case study (unifying the query stack)

Workstream: expansion-companies · Researched 2026-10-10 · Read-only research; no installation, ranking, or recommendation.

## Scope notes
Datadog is the observability-platform exemplar — and the case study in *unifying fragmented query engines*: from bottom-up specialized engines per data type to a composable stack (Arrow + Substrait + DataFusion), extended with the open-source **Distributed DataFusion** framework (2026). The primary source is Datadog's own engineering blog, fetched and read in full this pass.

## 1. Forensic reconstruction — how the machine actually works

### From specialized engines to a composable stack
- Claim: As Datadog expanded from metrics into traces, logs, profiles, RUM, and security signals, a bottom-up culture produced **specialized ingestion pipelines and query engines per workload** — performant but fragmented: different engines, different interfaces, no cross-dataset queries. Label: **Verified** — datadoghq.com engineering blog ("How we extended Apache DataFusion…"). Confidence: high (primary source, admirably candid about the fragmentation).
- Claim: The unification: **Apache Arrow** as the in-memory data format, **Substrait** as the execution-plan format, **Apache DataFusion** as the composable query engine — "converged" deliberately to preserve specialized performance while enabling shared capabilities and cross-dataset queries. Label: **Verified** (primary blog). Plain-English: instead of N query languages for N data types, one plan format and one engine framework with pluggable data sources.

### Distributed DataFusion: the framework, not the engine
- Claim: DataFusion executes per-query on a single machine — insufficient for Datadog's largest interactive workloads. **Distributed DataFusion** extends DataFusion's execution model across machines: it operates **exclusively on the physical plan** (leaving logical planning untouched), introducing **Stages** (plan sections separated by network boundaries), **Tasks** (a task is to a distributed plan what a partition is to a single-node plan), **NetworkShuffle** (global repartitioning across machines), and **NetworkCoalesce** (gathering streams to a coordinator). Open source, Rust, Apache 2.0, on GitHub and crates.io. Label: **Verified** — primary blog, read in full 2026-10-10. Confidence: high.
- Claim: The key design decision: build a **framework for building distributed engines**, not a distributed engine — users bring their own data sources, execution nodes, networking, and planning logic. Datadog explicitly rejected ClickHouse (not extensible enough), Spark/Ballista (intermediate materialization — wrong for low-latency interactive), and Trino (poor Arrow/Substrait integration, expensive at their scale). Label: **Verified** (primary blog). This is the strongest "build vs. buy" reasoning in the corpus — each rejection names the *specific* requirement the alternative missed.
- Claim: Production impact: heavy queries that struggled on a single node now complete **up to 10× faster** across machines "at the same total cost"; light queries stay single-node (the planner skips distribution when overhead outweighs benefit); benchmarks run on reproducible public infrastructure (12-node EC2 c5n.2xlarge, TPC-H/TPC-DS, Parquet on S3). Label: **Verified** (primary blog). Confidence: high that Datadog reports this; medium on independent reproduction (benchmarks are public and reproducible — the invitation is genuine).
- Claim: The team names its two hardest lessons: **when not to distribute** (distribution is overhead — network, serialization, coordination — paid only when the query needs it) and **how to preserve extensibility** while distributing. Label: **Verified** (primary blog). "Distributing queries was never the goal. It was a trade off required to support Datadog's scale."

### The 400+ integrations machine (context)
- Claim: Datadog maintains 400+ integrations — the ingestion breadth that makes the query-unification problem real (every integration is a data source the unified stack must serve). Label: **Corroborated** (widely reported; medium/@datagod.dev on the data-scale challenge). Confidence: medium-high.

## 2. Postmortem record — failures hunted down
- **No major public outage postmortem** at the Atlassian/Cloudflare depth was found for Datadog this pass. **Verified-absent** (searched; Datadog's blog is rich on architecture, thin on incident retrospectives).
- **The fragmentation itself as the postmortem:** the primary blog *is* a postmortem of the specialized-engine era — "different engines, different interfaces, and limited composability" stated as the problem, with the unification as the corrective action. The honest version of "we built it wrong the first time" is embedded in the architecture narrative. Label: **Inferred** (reading the blog as retrospective); the fragmentation facts are **Verified**.
- **Pricing as the chronic incident:** Datadog's pricing (per-host, per-GB ingest) is the industry's most complained-about — the "we cut our Datadog bill" genre is vast. This is a *business-model* postmortem happening in public: the pricing that funds the engineering is also the top churn risk. Not deep-dived technically here; noted as the adjacent failure mode. Label: **Corroborated** (community consensus); specifics not quantified in this pass.

## 3. Narrative audit — dismantling with receipts
- **"Open source" as strategy, not charity.** Distributed DataFusion is Apache 2.0 on GitHub — and the receipts show why: Datadog needs the *ecosystem* (datafusion-contrib, external contributors, hiring pipeline) more than it needs secrecy. The audit: open-sourcing the framework is a *talent and ecosystem* play that also happens to be good PR. Nothing wrong with that — but read it as strategy. Note the maturity signal from the spiceai ADR: the donated repo had ~50 stars, 14 contributors, "not yet ready for production" at donation — honest early open-sourcing, not a victory lap. Label: **Inferred** (audit synthesis) on **Verified** (blog) + **Corroborated** (spiceai ADR comparison table).
- **The build-vs-buy reasoning is the actual exemplar.** Most "why we built our own X" posts are rationalizations; Datadog's names four specific requirements and shows why each alternative (ClickHouse, Spark/Ballista, Trino) missed at least one — with the killer line that they weren't looking for a distributed query engine but *a framework for building one*. The audit credit: this is how build-vs-buy should be argued — requirement-by-requirement, with the rejected alternatives named. Copy the *argument structure*, not the decision. Label: **Inferred** on **Verified** blog.
- **"Up to 10× faster at the same total cost" — read the sentence.** The claim is carefully bounded: *heavy* queries, *up to* 10×, *same total cost* (i.e., more machines, same $/query). The audit: this is honest benchmarking language, and the public reproducibility (AWS setup anyone can rerun) is the anti-benchmarketing move. The caveat: TPC-H/TPC-DS are synthetic; your telemetry workload isn't. Reproduce before citing. Label: **Inferred** on **Verified** blog.
- **The missing postmortem culture as the gap.** A company that instruments *everyone else's* systems publishes no deep incident retrospectives of its own that this pass could find. The audit doesn't allege hidden outages — it notes the asymmetry: the observability vendor's own observability practice is unobservable. For a company selling "see everything," that's worth one raised eyebrow. Label: **Inferred**; the absence is **Verified-absent**.

## Transferable lessons
1. **Argue build-vs-buy requirement-by-requirement.** Name the rejected alternatives and the specific requirement each missed. "Framework for building one, not the thing itself" is the level of precision to aim for.
2. **Unify the plan format before the engine.** Arrow (data) + Substrait (plans) made DataFusion composable; the engine choice followed the contracts, not vice versa.
3. **Distribution is overhead — teach the planner when to skip it.** The best distributed system is the one that knows when not to distribute.
4. **Benchmark like you'll be audited.** Public datasets, public infrastructure specs, reproducible setups — the anti-benchmarketing playbook.
5. **Write the fragmentation postmortem.** "Different engines, different interfaces, limited composability" — naming the old architecture's failure honestly is what authorizes the new one.
