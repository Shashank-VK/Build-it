# 14 — Engineering Rules & Anti-Patterns

**Status:** report section; read-only synthesis, not adoption advice. **Source:** the rules workstream (2026-10-10) — `research/rules/01-engineering-rules.md` (34 rules), `research/rules/02-anti-patterns.md` (19 anti-patterns). Claim labels preserved exactly as assigned by the research (**Verified / Corroborated / Inferred / Proposed / Unknown**); nothing here is upgraded. Full per-rule entries (violations, enforcement detail, context) live in `research/rules/01-engineering-rules.md`; per-anti-pattern entries (impact, full counterexamples) live in `research/rules/02-anti-patterns.md`.

---

## 0. Classifications

- **Critical control** — violation can kill the product or company. Non-negotiable.
- **Release gate** — must be satisfied before a release ships.
- **Strong practice** — default for professional teams; skipping needs a reason.
- **Context-dependent recommendation** — apply when the context matches.
- **Company-specific convention** — documented at a specific company; adopt deliberately, not by default.

**Automatability legend:** ✓ = automatable (or substantially) · ◐ = partially automatable · ✗ = human judgment.

## 2. The 7 critical controls, in full detail

The non-negotiables — violations can kill the product or company.

### R-01 — Ship outcomes, not outputs
**The rule:** No significant build begins without a named, measurable customer or business outcome it is expected to move, and a falsifiable belief about why the build will move it. **Applies when:** any work consuming more than a trivial appetite; funded roadmaps. **Violation looks like:** a roadmap measured in "features shipped per quarter"; a launch with no success metric defined; "we'll figure out the metrics after launch." **Enforcement:** every initiative document names its outcome metric and target before resourcing; leadership reviews outcome movement, not output counts. **Automatable:** Partially — dashboards can track outcome metrics and flag launches with none defined; the judgment of *which* outcome is human.

### R-11 — Everything in version control; mainline always releasable
**The rule:** All production artefacts (code, config, infra, docs-that-matter) live in version control. The main branch is always in a releasable state: every merge keeps the build green and the suite passing. **Applies when:** always, from the first commit. **Violation looks like:** config edited directly in production; "don't deploy on Fridays because main is broken"; releases assembled by hand. **Enforcement:** branch protection (no direct pushes to main); CI must pass before merge; releases built only from tagged mainline commits. **Automatable:** Yes — branch protection, required checks, tag-only release pipelines. **Exceptions:** None. This is the floor.

### R-12 — One-step, reproducible builds; build, release, and run strictly separated
**The rule:** A release is produced by one command from a clean checkout, reproducibly. Build (compile artefacts), release (combine artefact + config), and run (execute in the environment) are distinct, auditable stages — the same artefact that was tested is what ships. **Violation looks like:** a release runbook with 14 manual steps; "the staging build is different from the prod build"; binaries built on a developer laptop. **Enforcement:** CI builds all release artefacts; the release pipeline promotes immutable artefacts between environments. **Automatable:** Yes — this rule is almost entirely automation. **Exceptions:** None for shipped software.

### R-13 — No AI-generated code reaches production unverified
**The rule:** Code produced with AI assistance is treated as untrusted input until a human (or a qualified independent check) has reviewed, tested, and understood it. The dividing line is review, not AI use: reviewed, tested, explainable AI-assisted code is normal software development; unreviewed output is not shippable. **Violation looks like:** "Accept All" on diffs; merged PRs the author cannot explain; AI-suggested packages installed without checking they exist. **Enforcement:** code review explicitly covers AI-assisted diffs; SAST/SCA/secrets scans run on every PR; dependency additions verified against registries. **Automatable:** Partially — scanners catch known-bad patterns; understanding and design review are human. **Exceptions:** genuinely throwaway prototypes (never merged to main); trivially reviewable boilerplate (review is cheap, not skipped).

### R-15 — Configuration in the environment; secrets never in code
**The rule:** Anything that varies between deploys lives in the environment, not the codebase. Secrets are never committed, never logged, never pasted into chats or prompts. **Violation looks like:** API keys in repo history; `.env` committed "temporarily"; secrets in AI chat transcripts and logs. **Enforcement:** secrets scanners on every commit/PR (block on detection); environment-based config required by the deploy pipeline. **Automatable:** Yes — pre-commit and CI secret scanning. **Exceptions:** None.

### R-21 — Least privilege by default, everywhere
**The rule:** Every identity — human, service, and AI agent — gets the minimum permissions it needs, for the minimum time it needs them. Defaults deny; access is granted explicitly and reviewed periodically. **Applies when:** IAM, service accounts, API keys, database roles, and especially agent tool permissions. **Violation looks like:** `admin` service accounts for read-only jobs; agents with production write access "temporarily" for six months; wildcard IAM policies. **Enforcement:** permission reviews on a cadence; agent tool manifests reviewed like code; alerts on privilege escalations. **Automatable:** Partially — IAM analysers flag excess privilege; right-sizing needs human judgment. **Exceptions:** break-glass emergency access — timeboxed, logged, reviewed after.

### R-24 — Backups exist, are monitored, and restore-tested
**The rule:** Production data is backed up on a schedule, backup *success* is monitored with alerts that are themselves tested end-to-end, and restores are rehearsed on a cadence. **Applies when:** any production data you cannot afford to lose or recreate. **Violation looks like:** "backups run nightly" with nobody checking; restore never attempted; alerts that fire into a dead mailbox. **Enforcement:** restore drills on a calendar; alert-path tests; RPO/RTO written down and verified. **Automatable:** Substantially. **Exceptions:** None for production data (ephemeral/cache data is explicitly classified as such — the classification itself is the control).

## 3. The 7 release gates, in full detail

Each must be satisfied (or formally excepted by a named owner) before a release ships. Gate precedence from the quality-gate system (§17): **NO-GO > NOT ASSESSED > GO** — an unknown is never a pass.

### R-09 — Threat-model before you build trust boundaries
**The rule:** Before building anything that crosses a trust boundary (auth, payments, PII, multi-tenant isolation, AI agents with tool access), produce a lightweight threat model: assets, actors, entry points, and how each is mitigated. Revisit when the boundary moves. **Evidence:** Shostack's discipline [Corroborated]; OWASP ASVS V1 [Verified]. **Enforcement:** security-verification template requires the threat-model section; release gate for sensitive systems. **Exceptions:** purely local, single-user, no-network prototypes; static content sites (still do the 10-minute version).

### R-18 — Critical paths are tested, and releases gate on the tests
**The rule:** The paths that must work (signup, payment, core workflow, data integrity) have automated tests, and a red suite blocks the release. Coverage is a side effect; the gate is "the critical paths are proven on every change." **Evidence:** Joel Test modernised [Verified]; CrowdStrike — the missing test for non-wildcard matching is exactly the untested critical path [Verified]; WHO/Pronovost — verification checklists as gates [Verified]. **Enforcement:** CI gates on the suite; flaky-test quarantine with owner and deadline. **Exceptions:** none for critical paths; non-critical paths carry lighter coverage with the gap recorded.

### R-20 — Every production change gets a second pair of eyes
**The rule:** No change reaches production without review by someone (or something qualified) other than the author. For high-risk changes — auth, money, data migration, security boundaries — the reviewer must be a qualified human, and AI-generated diffs get extra scrutiny, not less. **Evidence:** Perry et al. — AI-assisted authors are more confident *and* less secure, so the reviewer cannot be the same overconfident loop [Verified]; industry review research [Corroborated]. **Enforcement:** branch protection requiring review; risk-tiered reviewer requirements. **Exceptions:** automated, pre-approved change classes (dependency patch bumps within policy) — the *policy* was human-reviewed instead.

### R-22 — Meet ASVS Level 1 before any internet-facing deploy
**The rule:** Before an internet-facing application serves real traffic, it is verified against OWASP ASVS Level 1 (the automatable baseline: auth, session, access control, input validation, crypto, logging, config). Level 2 becomes the target as the product matures and handles sensitive data. **Evidence:** ASVS v4.0.3/v5.0.0 [Verified]; Pearce/Perry show the vulnerability classes ASVS covers are exactly what AI-assisted code gets wrong [Verified]. **Enforcement:** security-verification template structured on ASVS chapters; the gap register (pass/fail/N-A per requirement, owner, close date) is the release artefact. **Automatable:** substantially — L1 is designed for automated verification. **Exceptions:** none for internet-facing; truly local/offline prototypes defer with a written date.

### R-23 — Patch known vulnerabilities promptly; know your dependencies
**The rule:** Dependencies are pinned via lockfiles, inventoried (SBOM or equivalent), continuously scanned, and patched on a defined SLA by severity — critical reachable vulnerabilities same-day to days, not quarters. **Evidence:** Log4Shell and the CISA emergency directive [Corroborated]; ASVS supply-chain chapter [Verified]. **Enforcement:** SCA scanning in CI blocking on critical; patch-SLA tracked like any SLA; SBOM generated per release. **Automatable:** yes — scanning, inventory, even automated patch PRs. **Exceptions:** unreachable vulnerabilities (documented with reachability analysis, not assumed); EOL dependencies get a migration plan with a date.

### R-25 — Every release is reversible and rolled out progressively
**The rule:** Every production change can be undone quickly (rollback, feature-flag kill, traffic shift), and risky changes reach users progressively (canary / staged rollout / blue-green) rather than all at once. Rollback is rehearsed, not theoretical. **Evidence:** Knight Capital — rollback made it worse; no kill switch [Verified]; CrowdStrike RCA: "Template Instances should have staged deployment" [Verified]; Twelve-Factor IX disposability [Verified]. **Enforcement:** release-readiness checklist requires the rollback procedure and rollout plan; game-day the rollback quarterly. **Automatable:** substantially — progressive-delivery controllers automate canary analysis and automatic rollback on metric regression. **Exceptions:** irreversible-by-nature changes (data migrations, key rotations) get the *strictest* progressive treatment, not exemption.

### R-26 — Gate risky changes behind flags, not branches
**The rule:** Behaviour changes with uncertain outcomes ship dark behind feature flags with named owners and expiry dates, and are enabled progressively. Long-lived branches are the alternative you are avoiding. **Evidence:** DORA elite practice [Verified]; Knight Capital's flag *reuse* is the cautionary tale for flag hygiene [Verified]. **Enforcement:** flag registry with owner + expiry; CI flags stale flags; flags are config (R-15), never repurposed identifiers (R-16). **Exceptions:** truly trivial changes; changes that cannot be meaningfully split (then use progressive rollout instead).

## 4. The anti-pattern catalogue (all 19, condensed)

Every anti-pattern names: cause → warning signs → corrective action, plus a **counterexample** (the normally-discouraged practice done appropriately). Each is a default with named escape hatches, not a prohibition.

| **AP-13** | Incomplete responsive behaviour | R-03 | Desktop-first then "check mobile later"; testing only at the designer's viewport | Horizontal scroll on phones; tap targets needing a stylus; "just use the desktop site" | Mobile-first or mobile-concurrently; real devices at real viewports; responsive checks in visual QA and launch readiness | Internal desktop-only tools (documented, not assumed); early prototypes validating a desktop-only workflow — responsive on the explicit roadmap |
| **AP-14** | Misleading product demos | R-02, R-04 | Demo-driven development — optimising for applause rather than production reality; undisclosed fakery | Demo never touches real data; "we'll figure out scale/security/cost later"; demo-only code paths | Disclose what's real (reality inventory); demo on production-shaped data; separate validation demos (disclosed fake) from commitment demos (real only) | Wizard-of-Oz research with *disclosed* simulation (textbook method); pure vision pieces labelled as vision |
| **AP-15** | Missing UX states | R-03, R-19 | Designing only the happy path; "we'll handle errors later" (later never comes) | Blank screens during loads; silent failures; no empty states; destructive actions without confirmation | UX-states inventory designed per flow from the start (loading, empty, error, offline, permission-denied, rate-limited, destructive-confirm, success) | Only where the state is genuinely impossible — and "impossible" must survive five minutes of adversarial review |
| **AP-16** | Poor observability | R-28, R-29 | Instrumentation deferred to "after launch"; monitoring confused with alerting | Incidents discovered by customers; SSH-and-grep debugging; dashboards nobody trusts | Golden signals from day one; structured logs; dashboards before launch; alert on symptoms with runbooks | Throwaway prototypes (minimal logging, noted as debt) — but anything with a second user gets the four signals |
| **AP-17** | Unnecessary infrastructure | R-07 | Resume-driven architecture; confusing "web-scale" with "our scale"; premature distribution | Kubernetes for a CRUD app; microservices with one team; Kafka before the second consumer | Boring defaults (managed Postgres, monolith-first, PaaS); ADR for every infra choice; scale when measurement demands it | The product *is* infrastructure; load contractually guaranteed from day one; genuine regulatory/data-residency topology needs |
| **AP-18** | Unmeasured AI costs | R-32 | AI features priced by vibes; no per-request metering; demo economics mistaken for production | Nobody knows cost per user; API bill surprises monthly; no cost anomaly alerts | Meter per request, attribute per feature/cohort; cost in the launch checklist; caps and anomaly alerts | Tiny prototypes and internal tools — with rough metering even there |
| **AP-19** | Poor adoption / commercial viability | R-01, R-02, R-03 | Building without a distribution path; confusing signups with customers; unit economics as afterthought | Launches with no launch plan; free users never convert; CAC unknown; pricing by gut | Viability evidence in idea evaluation; willingness-to-pay tested before build; kill criteria honoured | Deliberately loss-led strategies with eyes-open economics and funded runway; open-source/public-goods where adoption *is* the outcome |

## 5. The 5 most instructive anti-patterns, expanded

### AP-09 — AI-generated code without verification
**Why it matters most now:** this is the failure mode the entire verification-bottleneck finding (§13) is about. Measured evidence: ~40% of AI completions vulnerable across CWE scenarios (Pearce et al. [Verified]; replication ~27%); AI-assisted developers produced *less* secure code while believing it *more* secure (Perry et al. [Verified]) — the confidence inflation is the mechanism, not a side effect; 56.4% of professionals report insecure AI suggestions are common (Snyk [Corroborated]); hallucinated package names are a supply-chain injection vector ("slopsquatting", Lanyado [Corroborated]). Karpathy's own scope was throwaway weekend projects; Willison's review boundary stands. **Corrective action:** the review/test/explain standard for *all* AI-assisted code; SAST + SCA + secrets on every PR; dependency additions verified against registries; agent instructions that cap autonomy and require verification steps. **Counterexample:** Karpathy's original scope — no users, no secrets, no network trust — and trivially reviewable boilerplate where the "review" is a glance (cheap, not skipped).

### AP-10 — Uncontrolled agents
**Why it matters most now:** the blast radius of a bug becomes the blast radius of the agent's permissions. Anthropic's guidance [Verified]: agents need well-designed tools, sandbox testing, guardrails, human checkpoints; start with the simplest pattern; prefer *workflows* (deterministic paths) over *agents* (autonomous) where the path is known. Knight Capital is the parable of automation without a kill switch [Verified]. The "lethal trifecta" framing (Corroborated, practitioner): private-data access + untrusted content + external communication is exploitable *by design* — remove one leg rather than perfecting a filter; OWASP's position is that prompt injection (LLM01) has no reliable fix [Corroborated]. **Corrective action:** tool manifests with least privilege; human approval for consequential actions; full action logging; sandbox-first testing. **Counterexample:** broad autonomy is fine in consequence-free sandboxes and read-only investigation agents whose worst case is a wrong answer — the control scales with consequence.

### AP-08 — Weak security
**Why it matters most now:** the vulnerability classes AI-assisted code gets wrong (injection, auth, crypto) are exactly what ASVS Level 1 gates — so this anti-pattern compounds AP-09. Hand-rolled auth/crypto, secrets in code, unpatched dependencies, and AI-generated security logic merged "on vibes" are the warning signs. Log4Shell showed a transitive logging dependency could be remote-code-execution in nearly everything [Corroborated]. **Corrective action:** threat model at design (R-09); ASVS L1 gate before internet-facing launch (R-22); secrets scanning, SCA, patch SLAs (R-23); *independent* review of AI-generated security code (R-13, R-20). **Counterexample:** only truly local, single-user, offline prototypes may defer hardening — with a written "not shippable" marker and a date; never for anything networked.

### AP-11 — Excessive automation
**Why it matters most now:** the same instinct that made AI code cheap makes automated *everything* tempting — and automated wrongness compounds at machine speed. Knight Capital's automation executed ~4M bad trades in 45 minutes [Verified] — automating a broken process just produces wrongness faster. SRE's toil discipline [Verified]: automate *toil* (manual, repetitive, automatable, tactical, no enduring value), not judgment. Knuth's warning against unmeasured optimisation [Corroborated]. **Corrective action:** automate toil first; keep humans in the loop for judgment calls; every automation gets monitoring, a kill switch, and an owner; measure before automating (R-17). **Counterexample:** deliberate over-automation in safety interlocks (the automation *is* the safety system) and high-frequency domains where human reaction time is the bottleneck — there it gets the engineering rigour of a safety system, not a script.

### AP-14 — Misleading product demos
**Why it matters most now:** AI demos hide governance, security, and cost gaps by construction (no guardrails, no cost accounting in demos), and AI-era procurement has a documented failure mode of "trust us, just deploy" replacing pilots [Corroborated]. The canonical failure shapes: Ovation (1983 — demo was fake) and Magic Leap (2016 — deceptive demos alleged, contested) [Corroborated]. **Corrective action:** prototype acceptance with a mandatory *reality inventory* — every capability shown marked real vs simulated, with anything unmarked assumed simulated and anything simulated disclosed wherever the demo is shown; demo on production-shaped data; separate *validation* demos (explicitly fake, disclosed) from *commitment* demos (real capabilities only). **Counterexample:** *disclosed* simulation is a legitimate textbook method (Wizard-of-Oz research — undisclosed fakery in research is fraud; disclosed simulation is method); pure vision pieces labelled as vision.
