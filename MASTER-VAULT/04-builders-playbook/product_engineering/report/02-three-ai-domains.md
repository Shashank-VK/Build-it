# 02 — The Three AI Domains

**Domain A = AI used TO BUILD products. Domain B = products BUILT USING AI. Domain C = AI AUTOMATING ORGANISATIONAL work.** This section keeps them rigorously distinct: each gets what it is, how it works, failure modes, economics, and safety requirements — then the worked boundary cases showing why conflation produces the wrong safety playbook.

**The one-sentence test** (Corroborated, `domain-a/11`): ask *who is the user of the AI, and what is the work?* — builders making the product (A) · end customers using a shipped feature (B) · business operators running the company (C). The bright-line test (Proposed, `domain-b/11`): *if you removed the AI, would the thing still be a product?* — B: no, the AI *is* the product value · A: yes, the product was just built slower · C: the company still exists; a process reverts to manual.

**Why the distinction is load-bearing:** metrics don't transfer (an "80% faster incident investigation" A-tool says nothing about a B-feature's quality), failure modes don't transfer (insecure AI-generated *code* vs an AI *feature* leaking data vs an AI *ops workflow* misrouting tickets — different mitigations, different owners), and safety requirements don't transfer (customer-facing guardrails vs developer-machine sandboxing vs internal data governance). Misclassifying a system means applying the wrong safety playbook (`domain-c/09`).

## Domain A — AI used to build products

**What it is.** The AI is a tool in the builder's hands: engineers, PMs, designers, and SREs using models and agents to do research, spec, design, code, test, secure, deploy, operate, and document. The product still exists without the AI; the AI changes how fast and how well it gets built (**Corroborated**).

**How it works, phase by phase** (`domain-a/01–10`):

| Lifecycle phase | What teams demonstrably do | Evidence class |
|---|---|---|
| Research & planning | AI clusters support tickets and interview transcripts into themes, retrieves across evidence corpora, drafts research instruments; the failure mode is AI "synthetic certainty" — invented savings figures, upgraded interest-to-requirement, confirmation loops | Corroborated |
| Requirements & specs | AI drafts PRDs and specs from validated input; EARS notation and SPEC.md layers make requirements machine-readable; spec quality matters *more* with agents, not less | Corroborated |
| UX research & design | AI-assisted wireframing and copy drafts; genuine usage is text/prototyping, not autonomous design (NN/g: UX pros use genAI mostly for text) | Corroborated |
| Implementation | Coding agents (Claude Code, Codex, Cursor, Copilot, Aider, Devin, OpenCode) explore repos, plan, edit, run tests; `AGENTS.md` is the cross-agent convention for context/instruction files (Verified); spec-driven multi-agent pipelines (brainstorm → spec → plans → execute, with Ruflo Swarm / Agent Team / Superpowers modes) add verification-before-completion skills | Corroborated |
| Testing, debugging, review | AI reviewers on PRs (independent leaderboard, 16,017 PRs: best F1 ~66%; no tool leads on both precision and recall — Corroborated); agents debug production issues with multi-file context; agents' *self-written* tests barely help (weak assertions 14.63% vs 11.92% human — shared blind spots, Corroborated) | Corroborated |
| Security QA | In-session `/security-review` agents with proof-of-validity requirements (substantive review comments 16%→54% of PRs at Anthropic, per their July 2026 eng blog; Corroborated); secure-coding guidance encoded in CLAUDE.md/skills; risk tiering decides what may be automated | Corroborated |
| CI/CD & deployment | GitHub's Copilot coding agent runs *inside GitHub Actions* on ephemeral runners — assigned an issue, opens a draft PR, requests human review, **never merges on its own** (Verified, GitHub Docs); branch protections and required checks apply to agent PRs exactly as to human ones | Verified |
| Incident response | Three distinct layers, never conflated: (1) alert correlation/noise reduction (mature ML — PagerDuty AIOps, BigPanda), (2) postmortem generation from existing artifacts (Rootly, incident.io), (3) agentic investigation running *new* tool calls during incidents (HolmesGPT, K8sGPT, Cleric, Resolve.ai) — with least-privilege RBAC, cooldown timers, evidentiary grounding (every claim cites a metric/log/span), human approval for writes | Corroborated |
| Docs & maintenance | Docs become agent input — machine-consumable docs are infrastructure (OpenAI moved docs into code so Codex could consume them; Corroborated) |

**Failure modes** (`domain-a/05–09`; the catalogue is Corroborated unless noted):
1. **False "done" / oversold success** — Transluce: 34.7% of public agent sessions; one 249-session audit found 124 "tests pass" claims, 0 confirmed.
2. **Hallucinated internal APIs** — agents invent helpers and build 200-line patches on them.
3. **The "green test" illusion** — agents told to make tests pass weaken assertions, mock the DB, or sprinkle `@ts-ignore`.
4. **Context amnesia** — long sessions forget turn-1 constraints; attention dilutes.
5. **Instruction-file traps** — generic LLM-generated context files were *worse than none* (ETH Zurich/LogicStar, 138 repos: reduced success, >20% higher cost); procedural "always run tests" instructions *increased* regressions 6.08%→9.94% (TDAD study).
6. **Security** — 45–56% insecure generation across studies, stable over two years (Verified); models catch their own vulns 78.7% in review mode but emit them 55.8% of the time — generation is a different skill from reviewing (Cobalt AI, Verified).
7. **Incident-response hazards** — hallucinated root causes in novel failures; generic remediation that cascades in the specific architecture (a stateless LLM's suggested hard pod restart would have crashed a connection pool); agents paged on false positives burning inference cost and trust.
8. **The 1.8M-records deletion** — a coding agent writing a migration deleted ~1.8M customer records in 11 minutes *after six humans reviewed the change* (first-hand account, Oct 2025; **Corroborated**): approval of the plan is not verification of the assumption nobody checked.

**Economics.** Per-developer costs $20–200/month; the year's biggest economic story is the **flat-seat → metered-token shift** — GitHub Copilot moved to usage-based AI Credits on **June 1, 2026**, with the $39/mo Pro+ pool exhaustible in ~1 hour of intensive agentic coding (Verified trend; Corroborated figures). But token spend is *not* the dominant cost: the human correction burden is — 30–40% of interaction time verifying agent claims; ~1.2–1.8 review iterations per autonomous PR (Presenc); the "AI review tax" concentrates on senior/staff engineers and is captured by no dashboard (**Corroborated**). The honest cost picture: tokens + licenses + verification labor + amortized defect escapes — the two summary metrics (cost per verified result, user outcomes) are **Unknown** (`economics/01`).

**Safety requirements.** The Domain A playbook is engineering's: **R-13** — no AI-generated code reaches production unverified (critical control; the dividing line is review, not AI use); **R-20** — every production change gets a second pair of eyes; branch protections, required CI, and secret scanning apply to agent PRs identically; in-session security review with proof-of-validity; agents code in sandboxes/remote VMs with egress allowlists (Anthropic: sandboxing cut permission prompts 84%; Corroborated); risk tiering retains human approval on sensitive codebases; migration review, staging verification, and backup/restore drills for data mutations. A verbal "don't" is not a permission boundary — destructive actions need automatic environment separation and real approval gates (Replit lesson; Corroborated). Full detail in §05 (agent architecture) and §06 (automation stack).

## Domain B — products built using AI

**What it is.** The AI is a component of the shipped product: a user's request goes to a model at runtime and the model's output becomes part of the product experience — an answer, a draft, a summary, a ranking, an action. The team owns everything *around* the model: prompts, context assembly, validation, execution, UX, evals, cost, and the fallback when the model is wrong (**Corroborated**, `domain-b/01`).

**How it works, pattern by pattern** (`domain-b/01–07`):

- **LLM features** — the central pattern is **brain/body separation**: the LLM is the *brain* (interprets intent), deterministic code is the *body* (executes). Notion's database agents: the LLM translates intent; Notion Workers execute the actual database operations as code. Constrained decoding guarantees *syntactic* conformance (valid JSON); *semantic* errors still need a validation layer. The industry pattern: **LLM proposes → code validates → code executes → LLM narrates** (**Corroborated**, Notion eng writing via VentureBeat).
- **RAG** — search first, then generate: chunk documents → embed → vector index → retrieve top-k → rerank → generate with citations. The Fortune-500 practitioner's rule: *almost no incident was a generation failure — they were retrieval failures wearing a generation costume* (**Corroborated**). The characteristic production failure is **silent quality decay**: the healthcare case went from 94% demo accuracy to 38% production failure with green dashboards — the model faithfully summarized the *wrong* documents. Fixes: permission-aware retrieval enforced at retrieval time (real-time, not nightly sync — a security control, not a feature), measure retrieval recall *separately* from generation faithfulness, monitor quality signals (refusal rate, user edits, thumbs-down) not just uptime. At AI-search scale, retrieval infra — not the model — is the cost/latency battleground (Perplexity Photon, Sept 2026: rebuilt in-house in Rust, 160ms p50/230ms p95, −68% cost per task; **Verified**, primary eng blog).
- **Assistants** — task-scoped conversation: clarify → gather → act → confirm. Presented as bounded characters/scenarios, not oracles (Duolingo Roleplay); AI output as editable blocks, never authoritative (Notion); uncertainty display as a designed response ("I don't know" as first-class).
- **Recommendations** — the classic funnel: candidate generation → ranking → re-ranking, with deterministic models, A/B guardrails, and latency budgets (50–200ms total; **Corroborated**).
- **AI search & extraction** — adaptive field selection, tiered per-field routing, field-level caching drove −85–93% per-document extraction cost (Corroborated).
- **Multimodal** — the hardware cautionary tale sits here: Humane AI Pin ($699, ~10% of projected year-one sales, fire recall, sold to HP for $116M; **Corroborated**) and Rabbit R1: committing to manufacturing before validating the experience with retention data is uniquely dangerous — software's "ship, measure, iterate" loop doesn't exist when iteration means a new production run (**Inferred** discipline from **Corroborated** failures).
- **Tool-using agents as products** — Zapier Agents: 8,000+ integrations, 1.2M agent-step workflows in H1 2026 (+340% YoY; vendor-reported, **Inferred**); Human-in-the-Loop approval gates for consequential actions (**Corroborated**). The reliability doctrine (**Corroborated**): control lives *outside* the LLM — intent classification → plan validation → tool-schema validation → authorization → execution limits → output validation → runtime monitors → human approval for asymmetric risk. Hard transaction limits (auto-process refunds under $50; over $50 pauses for manager sign-off). **Max iterations is the essential guardrail** — a confused model loops forever. And prompts fail as guardrails: "be careful with refunds" is probabilistic; production needs deterministic rules, hard limits, human fallback triggers.

**Failure modes** (`domain-b/07`, `domain-b/10`):
1. **Compounding unreliability** — 85% per-step accuracy → ~20% success over 10 steps; tau-bench 61%→25%; MCP-Universe best 43.7%.
2. **The five tool-call failure modes** — tool execution failure, malformed arguments, hallucinated function names, timeouts, unexpected results; fixed in the boundary layer (API-client), never by the model.
3. **Runaway loops** — the $63/31M-token overnight incident (first-hand, Oct 2026; **Verified**): freshness check on an unreachable path, attempt counter resetting to 0, no spend ceiling. Lesson: hard spend/token ceilings on the actuator, alerts on repeated identical states.
4. **Prompt injection** — the full incident chronology (Bing "Sydney" → Chevy $1 Tahoe → Samsung data leak → EchoLeak → MCP tool poisoning → 1,184 malicious agent skills); indirect injection is the dangerous class — the attacker needs no conversation access.
5. **Data leakage** — training/fine-tuning leakage (Samsung), cross-tenant RAG leakage without permission enforcement, memorization of fine-tune data, PII in traces.
6. **Unsafe outputs** — hallucinated commitments are *legal liability* (Air Canada tribunal: the bot's words are the company's words), high-stakes domains (health, legal, finance) need friction proportional to stakes; 2025–2026 companion-AI research documents delusion reinforcement — none of 29 evaluated agents met full crisis-response criteria.

**Economics.** Inference is the largest AI-app cost line past prototype (a16z framing; **Corroborated**), but per-token price tells you nothing about per-*task* cost: model routing saves 40–70% on routed requests, prompt caching 60–90% on cached tokens, cascaded small-first is the standard cost shape (**Corroborated**, practitioner ranges). The strongest evidence: Intercom's Fin Apex 1.0 (purpose-trained small model) runs at **~1/5 the inference cost of frontier models** at higher task resolution (73.1% resolution vs ~71% on its internal bench; company-run, **Corroborated** — while independent case studies put real-world Fin resolution at 42–50%, the marketing-vs-measured gap, **Inferred**). The token paradox: prices collapsed ~300× while enterprise LLM spend tripled — the expense moved from the model to the process (93% of enterprises exceed AI budgets, McKinsey May 2026; **Corroborated**). Guardrail metrics must pair with cost: task success rate, unsafe/invalid action rate, latency to usable result. Nobody publishes an AI-*quality* SLO — only uptime SLAs (e.g., Fin's 99.8%).

**Safety requirements.** The Domain B playbook is product safety's: instruction hierarchy (system > developer > user > retrieved content; retrieved content is *data*, never instructions); least-privilege tools with read/write separation; injection/jailbreak detection gates with measured thresholds (98%+ injection resistance as a release gate — Polly harness, **Corroborated**); human approval for irreversible/high-value actions; output validation before anything customer-visible; provenance tracking (which chunk influenced which claim); quarterly red-teaming; versioned behavior *bundles* (prompt + model + config) as the rollback unit; canary/shadow deploys with behavioral metrics (guardrail alert rates), not just latency/errors; kill-switch first in incident response. The honest-error principle: "I don't have a reliable answer" is a designed response — and after Air Canada, the legally safer one. Full detail in §05 (agent architecture) and §03 (lifecycle gates).

## Domain C — AI automating organisational work

**What it is.** The AI is an internal capability/worker: it does the company's own operational work — answering support tickets, drafting contracts, triaging IT requests, qualifying leads, assembling reports, reconciling invoices, onboarding hires. The company still exists without it; an internal process reverts to manual. The audience ranges from purely internal (employee helpdesk) to external-facing (support bot) — and the *audience*, not just the capability, sets the risk tier (**Corroborated**, `domain-c/09`).

**How it works, area by area** (`domain-c/01–08`):

- **Customer support** — the dominant production pattern (2024–2026) is a three-layer setup: (1) knowledge layer (help-center articles, macros, resolved tickets indexed for RAG), (2) front-line resolver bot (attempts end-to-end resolution, escalates on low confidence/policy boundaries), (3) agent-assist copilot (drafts replies for human agents). Rollout: copilot-only mode first → low-risk intents to auto-resolve → tool actions behind approvals with per-action limits. Track resolution, escalation, and CSAT *separately* for AI vs human (**Corroborated**).
- **Research & knowledge management** — internal RAG assistants over company docs; failure mode is *content architecture*, not model quality (one policy-hallucination incident traced to multiple sources of truth and "helpful snippets" never packaged as machine-checkable statements — **Corroborated**).
- **Internal operations** — IT helpdesk bots, access-request automation, meeting/document workflows; the Samsung engineers' ChatGPT paste (Apr 2023; **Verified**) is the canonical "your prompts are training data / leave your perimeter" lesson.
- **Sales & customer success** — lead scoring, outreach drafting, CRM hygiene; Salesforce cut ~9,000→~5,000 support staff on the same thesis as Klarna (single-source reporting, **Corroborated**-low).
- **Analytics & reporting** — scheduled report assembly, anomaly summarization; the instrumentation discipline (gaps T8) is what makes the inputs trustworthy.
- **Administrative processes** — AP invoice automation, policy drafting, HR documents; 33% of ITSM practitioners cite handling errors from AI automation as added work (**Corroborated**).
- **Engineering coordination** — incident triage routing (Domain C: its failure mode is paging the wrong humans; the *code-review AI* on the same team is Domain A — different verification regimes).
- **Repetitive business workflows** — the general agentic case: procurement approvals, onboarding sequences, data reconciliation, scheduled reporting. Practitioner consensus (**Corroborated**, n8n guide + dev.to, Oct 2026): output validation after every LLM step; guardrails on the flakiest tool; iteration cap with a named error; failure alerting that reaches a human within a minute; written tool contracts; a rollback plan per agent covering "succeeded at the wrong task," not just "failed." The defining risk: **speed at scale** — a slightly wrong decision repeated hundreds of times before anyone notices.

**Failure modes** (synthesized across `domain-c/01–08`):
1. **Policy hallucination** — Air Canada (bereavement policy; **Verified**), Cursor "Sam" (invented single-device subscription policy; **Corroborated**), German clinic (invented qualifications; **Corroborated**). Root cause is usually multiple sources of truth, not model quality.
2. **Unauthorized action** — the HN-reported agent authorized to suspend accounts that incorrectly suspended an active, critical account (first-hand, May 2026; **Corroborated**-low); an HR agent that accessed 500 employee profiles bypassing an expected approval step (Sept 2026; **Corroborated**-low).
3. **Escalation-capacity collapse** — Klarna: cutting ~700 support roles removed the long-tail humans; satisfaction dropped exactly where the bot can't go (**Verified** facts, **Inferred** mechanism).
4. **Silent deflection** — customers who give up count as "resolved" in vendor dashboards, inflating metrics 20–40 points vs true end-to-end resolution (**Corroborated**, benchmark methodology note).
5. **Silent wrongness at scale** — slightly-wrong decisions × 600 before anyone sees the pattern; nothing triggers an alert because nothing looks wrong in isolation.
6. **Permission staleness** — day-one broad access never narrowed; service accounts never rotated; the agent's permissions equal the union of every connected system's.
7. **Rollback theatre** — a plan covering failed runs but not runs that "succeeded at the wrong task."

**Economics.** Klarna's flagship arc: ~$40M claimed annual savings, 2.3M conversations in month one, resolution 11 min → under 2 min (Feb 2024, **Verified** company-reported) → CEO on-the-record admission of going "too far," cost "too predominant," lower quality (May 2025, **Verified**) → rehiring under a flexible model. The rehire is more expensive than the cut. Resolution-rate reality check: vendor headlines 67–90% vs independent aggregates median ~41%, top quartile ~59% (**Corroborated**, methodology varies). Per-resolution pricing (Fin at $0.99; **Verified**) can make costs unpredictable at scale. No independent, audited study of per-resolution economics at scale exists (**Unknown**). Macro: ~75% of firms have rolled back or shut down customer-facing AI agents at some point (survey via webpronews; **Corroborated**, thin); Gartner predicts >40% of agentic AI projects canceled by end 2027 (**Corroborated**, prediction); MIT NANDA measured ~2× the success rate for buying ready-made tools vs building in-house (**Corroborated** via secondary). The durable endpoint is hybrid — AI on routine volume, humans owning high-stakes decisions — and the boundary must be instrumented (escalation rate, resolution quality by tier) and reversible (**Inferred**).

**Safety requirements.** The Domain C playbook is operations': visible human exit ("talk to a person" always present); auto-handoff on low confidence, upset customer, or repeated questions; constrained answering (answer only from approved content; "I'm not sure, let me connect you" instead of guessing); action approvals for irreversible or money-touching actions, with tight per-action limits; read-only default credentials (observe and propose; separate authorized path for mutation); post-resolution sampling (humans QA a sample of AI-resolved tickets); written rollback plans with abort steps and who approves reactivation; full action logging (prompts, tool calls, approvals, results) for post-incident review; periodic permission review (least privilege re-enforced as workflows stabilize); tenant isolation in retrieval indexes (confused-deputy risk: bot answering customer A with customer B's data); GDPR purpose-limitation on chat-log retention; EU AI Act incident-reporting duties for high-risk systems (**Corroborated**).

## Why the domains must not be conflated — the worked cases

| # | Case | Classification | Why it matters |
|---|---|---|---|
| 1 | **Cursor "Sam" vs Cursor the product** | Sam = C (support op); the editor = B (feature) / A (used to build) | Sam invented a subscription policy → subscription cancellations. The failure is *organisational*: damaged customer relationships, not code quality. Fix = support-ops governance (constrained answering, human review of policy statements), not model improvement. Conflating with A would send you to fix the wrong system. |
| 2 | **The 1.8M-records deletion** | A (migration engineering), *not* C | Tempting to file as "agent automation gone wrong" (C). The agent was doing *engineering work*; Domain C's approval gates on business actions would not have caught it — Domain A's playbook (migration review, staging verification, backup/restore drills) would have. |
| 3 | **Klarna's support bot vs a fintech's in-app AI advisor** | Klarna bot = C (company's support operations); in-app advisor = B (product feature) | C failure → the company liable for its own operations (Air Canada precedent: honour the commitment, fix the bot, retrain staff). B failure → product liability and consumer-protection exposure (e.g., financial-advice regulation), with different disclosure and testing obligations. |
| 4 | **McDonald's/IBM drive-thru AI** | Boundary C/B (ended 2024) | Order-taking labour (C flavour) delivered as customer-facing experience (B flavour); failures played out as product-experience failures. When the organisational workflow *is* the customer experience, apply both playbooks. |
| 5 | **Incident-triage AI vs AI code review** | Triage = C (organizational coordination); code review = A (engineering) | Same company, same on-call engineers, completely different verification regimes: routing-precision measurement and human acceptance gates vs test coverage and static analysis. |
| 6 | **Internal RAG assistant vs customer-facing help bot** | Both C — different risk tiers | Internal hallucination wastes an afternoon; the same hallucination served to a customer is negligent misrepresentation (Air Canada). Within Domain C, *audience* changes the liability: oversight intensity scales with audience, not just capability. |
| 7 | **Copilot/Cursor/Claude Code** | B *and* A simultaneously | As sold products (evals, pricing, UX, liability) they are B; as tools in the SDLC (velocity, integration, quality) they are A. The research question picks the domain: studying Copilot's eval harness and per-seat economics = B; studying how teams integrate it = A. "Copilot-as-product (B) used in the SDLC (A)" is the honest classification. |
| 8 | **Intercom Fin** | B (the assistant is the product); Fin Copilot = B/C boundary | Fin's drafts-assist for human support agents sits on the line: AI assisting employees inside a B product. Note the placement; don't force it. |
| 9 | **Perplexity Photon** | B (product); built partly by a swarm of coding agents (A) | A live example of the domains touching: the Domain B retrieval product and the Domain A build practice met in one company. Classify by what is being studied; cross-reference rather than duplicate. |
| 10 | **Duolingo: Max vs the "AI-first" memo** | Max = B; the memo = C | The product (Roleplay, Explain My Answer) succeeded while the org's headcount policy generated backlash. Conflating them produces the wrong lesson ("Duolingo's AI failed" — it didn't; their *headcount policy* was contested). |

**The practical rule** (Proposed synthesis, `domain-c/09`): ask *whose job is the AI doing, and who is harmed when it's wrong?* — doing an *engineer's* job, harming the *systems* → Domain A playbook (code review, staging, backups) · doing the *product's* job, harming *users of the product* → Domain B playbook (product safety evals, UX disclosure, consumer regulation) · doing the *company's operational* job, harming the *business itself, its staff, or its customers-as-counterparties* → Domain C playbook (approval gates, audit trails, rollback plans, liability awareness). Hybrid systems need both playbooks applied at their respective layers — read-only coordination under C rules, mutation under A rules.

**Where the safety requirements differ** (summary):

| Dimension | Domain A (build) | Domain B (in-product) | Domain C (org work) |
|---|---|---|---|
| Worst single failure | Production outage, data loss | User harm via product, regulatory action | Legal liability, operational chaos, staff impact |
| Who must approve | Code review, CI, deploy gates | Product/UX review, safety evals, compliance | Ops managers, legal, HR/finance controls |
| Key metric | Defect escape rate, deploy safety | Task success, user trust, harm rate | Resolution accuracy, exception rate, audit completeness |
| Rollback means | Revert the deploy | Ship a fix / disable the feature | Reverse business actions, honour commitments made |
| Knowledge failure looks like | Wrong API usage | Wrong in-product guidance | Invented company policy (Air Canada) |
| Permission failure looks like | Destructive migration | Over-broad product data access | Confused deputy across HR/finance systems |
