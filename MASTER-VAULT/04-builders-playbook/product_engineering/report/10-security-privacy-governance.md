# 10 — Security, Privacy & Governance

*Application security from design through production, AI/agent security, and the privacy/legal floor. Synthesised from the security research stream (§§24a–24e, §25 classification index). Claim labels — **Verified** / **Corroborated** / **Inferred** / **Proposed** / **Unknown** — are preserved; nothing upgraded. This is research, not legal advice.*

**How to read the classifications:** every control is tagged with its §25 class — **legal obligation** (in a specified context) · **critical safeguard** (failure is routinely severe) · **risk-dependent** (required only where the threat model warrants) · **recommended** (strong default, skippable with a named owner and rationale) · **optional** (enhancement) · **harmful if misapplied** (the control backfires when applied wrongly). Classification is **contextual, not universal** — the class shown is for the stated context (see §7).

## 2. Auth & account

| Control | §25 class | The essential detail |
|---|---|---|
| **Adaptive password hashing** — Argon2id first (m=19 MiB, t=2, p=1); scrypt if unavailable (N=2^17, r=8, p=1); bcrypt only for legacy (cost ≥10, 72-byte limit); PBKDF2 only for FIPS-140 (≥600k iterations). Server-side only; never MD5/SHA-1/plaintext; never reversible encryption | **Critical safeguard** | **Verified** (OWASP Password Storage Cheat Sheet). Bcrypt alone is "legacy-acceptable," not best practice; MD5/SHA-1/unsalted is a critical failure |
| **Throttling + progressive delays, NO universal hard lockout** — per-account + per-IP throttling, bot challenges, step-up by risk; notify on authenticator disable | **Risk-dependent** (parameters); *absence* of any throttling is a critical gap | **Verified** (NIST). A universal hard lockout is an attacker-operated lockout button — **harmful if misapplied** (**Corroborated**) |
| **Account-enumeration resistance** — identical messages, timing, and status codes for existent vs non-existent accounts on login/registration/reset; dummy-hash comparison to equalise timing; constant-time token comparison | **Recommended** → critical for high-value targets | **Corroborated** |
| **Secure session cookies** — CSPRNG IDs (≥64-bit entropy, opaque); `Secure; HttpOnly; SameSite=Lax\|Strict`; **rotate ID at every privilege change** (login, role change) against fixation; idle + absolute timeouts enforced **server-side**; logout invalidates server-side; password/role change kills other sessions; JWTs need signature **and** `iss`/`aud` verification; no long-lived auth tokens in `localStorage` | **Critical safeguard** | **Corroborated** (OWASP Session Management Cheat Sheet). Common real findings: sessions surviving logout ("cosmetic logout"), fixation, missing SameSite |
| **Password-reset tokens** — CSPRNG, ≥128-bit entropy, single-use, TTL in hours (not days), **stored as a hash** server-side; invalidate all sessions on password change | **Critical safeguard** | **Corroborated**. Predictable reset tokens → full account takeover (standard critical bug-bounty finding) |
| **MFA where warranted; phishing-resistant preferred** — FIDO2/WebAuthn/passkeys over SMS/voice OTP (SIM-swap); require for admin/payment/high-value; step-up auth for sensitive actions; **audit fallback paths** (an email/SMS fallback can bypass the primary factor's assurance) | **Risk-dependent** → critical for privileged accounts | **Corroborated** (NIST AAL model). SMS-OTP deprecation status: **Inferred** |
| **Security questions / knowledge-based recovery** | **Harmful if misapplied** | **Verified** (NIST forbids unauthenticated-accessible hints) — creates a weaker second credential |
| **Forced periodic rotation + composition rules** | **Harmful if misapplied** | **Verified** (NIST: SHALL NOT). Empirically produces weaker, predictable passwords (`Summer2024!` → `Summer2025!`). Prefer length + breach-corpus checking |
| **Security-event logging for auth** — log logins, MFA events, resets, anomalies; **never log secrets/tokens**; protect log integrity; monitor for stuffing patterns. Note: ASVS 5.0 L1 has zero logging requirements | **Recommended** → **legal obligation** where breach-detection duties apply | **Verified** (ASVS chapter analysis) |

## 3. App & API

| Control | §25 class | The essential detail |
|---|---|---|
| **Server-side input validation on every trust boundary** — type/length/range/format for REST, GraphQL, gRPC, webhooks, imports. Client-side validation is UX, not a control | **Critical safeguard** | **Corroborated** |
| **Parameterised queries; context-appropriate output encoding** — prepared statements everywhere; encode for the *sink* (HTML vs JS vs URL vs SQL-parameter). No single "sanitize()" is correct everywhere | **Critical safeguard** | **Corroborated** |
| **Authorisation on every protected operation** — authN *and* object-level authZ per endpoint (BOLA/API1, BFLA/API5); per-object ownership checks + per-function role checks; never rely on client-side gating or "hidden" routes; maintain an API inventory (shadow/zombie APIs are a named risk — API9) | **Critical safeguard** | **Corroborated** |
| **Mass-assignment prevention** — explicit writable-field allowlists (e.g., Zod/Pydantic schemas); never bind request bodies directly to ORM models (`{"role":"admin"}` must be ignored) | **Critical safeguard** | **Corroborated** |
| **Request size/time limits; rate limits; anti-automation** — body-parser caps, timeouts, upload limits; per-user *and* per-IP signals (per-IP-only is bypassed by distributed attacks — a known false-negative); quotas on signup/purchase/comment flows | **Recommended** → critical for metered/expensive endpoints | **Corroborated** |
| **CSRF defenses where the auth model requires it** — `SameSite=Lax` + Origin checks + synchronizer tokens for cookie auth. Bearer-token APIs are not CSRF-exploitable (there, XSS is the enemy) — demanding CSRF tokens there is complexity without benefit | **Risk-dependent** | **Corroborated** |
| **Security headers; HTTPS; narrow CORS** — HSTS, CSP, `nosniff`, Referrer/Permissions-Policy, frame-ancestors; TLS 1.2+ minimum, HSTS site-wide, never disable TLS verification; CORS allowlist-only (never `*` + credentials) | **Recommended** (headers/CORS) · **critical** (HTTPS) | **Corroborated** |
| **Upload restrictions; path-traversal prevention** — validate by content sniffing (magic bytes), not extension; size limits; store outside web root with random names; never execute uploaded content; canonicalize + jail paths, reject `..`/absolute/encoded sequences | **Critical** where upload/traversal-exposed; risk-dependent otherwise | **Corroborated** |
| **Webhook verification; replay/idempotency** — HMAC signature verification (constant-time compare), timestamp skew windows, per-endpoint secrets; idempotency keys on mutating/payment endpoints prevent double-charge/double-apply | **Recommended** → critical for payment/state-changing webhooks | **Corroborated** |
| **No sensitive data in errors; server-side price/payment validation; dependency scanning** — generic client errors (A10:2025 elevates error-handling failures to a top-ten category); never trust client-supplied prices/totals; verify gateway webhooks before fulfilment; CI dependency + secret scanning with fail-on-critical; SBOM | **Critical** (payments/secrets) · **recommended** (deps) | **Corroborated** |
| **SSRF controls** — never fetch user-supplied URLs without host/scheme allow-list; block private/link-local/metadata IPs (`169.254.169.254`); HTTPS-only; don't hand-roll IP parsers; pin DNS check→use | **Critical** where user-influenced server-side fetching exists | **Corroborated** |

## 4. Database & secrets

| Control | §25 class | The essential detail |
|---|---|---|
| **Privileged secrets out of client code** — service-role/admin keys server-side only; never in `VITE_*`/`NEXT_PUBLIC_*`/`EXPO_PUBLIC_*` (bundlers inline them); scan commits/PRs for hardcoded secrets; never log tokens/passwords/session IDs | **Critical safeguard** | **Corroborated** |
| **RLS enabled with correct policies where the data API is reachable** — the publishable/`anon` key (`sb_publishable_*`) is **public by design**; security comes from Row-Level Security, not key secrecy. New tables ship with no policies — verify by querying with the publishable key while signed out (rows back = policy failure); migration-time policy gate | **Critical safeguard** | **Verified** real incident (HoopHub #1038, July 2026: Supabase's own `rls_disabled_in_public` CRITICAL alert fired; the public anon key granted read+insert+delete on every public table, exposing live PII emails) + **Corroborated** guidance |
| **Do NOT flag publishable keys in client config as vulnerabilities** | Classification hygiene (anti-finding) | **Corroborated** — flagging the public key is a misclassification that breeds false comfort ("nobody has the key") while the real issue — missing RLS — goes unaddressed |
| **Least-privilege DB roles; scoped service auth** — separate migration vs runtime roles; no SUPERUSER for app roles; per-service scoped short-lived credentials; audience-checked tokens (token-passthrough without audience validation is a live confused-deputy attack pattern) | **Recommended** | **Corroborated** |
| **Exposed-credential rotation** — any secret reaching a client bundle, public repo, log, or error message is **compromised**: revoke → rotate → move server-side → audit usage logs → breach-notification assessment per jurisdiction | **Critical safeguard** (response control) | **Corroborated** |
| **No directory listing / unnecessary admin routes; DB policy review cadence** — disable listing; remove default/admin/debug routes from prod or gate behind authN + network controls; review DB policies on schema change and on cadence | **Recommended** | **Corroborated** |

**Three-bucket separation rule (Corroborated):** (1) **browser-safe** — project URL + publishable key; (2) **server-only** — service-role/secret keys, env store at most, bundle scan on every PR; (3) **per-request** — the user's session JWT, transported in cookies by the server client, never in `localStorage` for long-lived tokens.

## 5. AI & agent security

**The foundational finding (Corroborated):** prompt injection has no patch-style fix. Greshake et al. (2023, arXiv 2302.12173) showed that processing untrusted retrieved data is *analogous to executing arbitrary code* — retrieval merges data and instructions into one undifferentiated channel; the attacker never enters the session (no account, no rate limit), they place text where the agent will read it. Mitigations are architectural (separation, filtering, oversight), not a code change.

| Control | Threat addressed | §25 class |
|---|---|---|
| **Treat all retrieved/external content as untrusted data, never instructions** — delimit untrusted content in context; sanitise ingested data; integrity checks on persistent memory; memory isolation between agents/sessions | Indirect injection (self-forwarding worms, memory persistence, C2 demonstrated on real products) | **Critical safeguard** (any agent reading untrusted content) |
| **Sandboxing for code execution** — hardware-enforced, zero-access where feasible; no network/secret access unless the task requires it; egress filtering | Unexpected code execution → RCE (ASI05) | **Critical** when agents execute code; n/a for text-only agents |
| **Tool allowlists; signed/pinned manifests; re-approval on change** — pin/hash `tools/list`; treat tool descriptions and annotations (`readOnlyHint`) as untrusted; validate parameter schemas. MCP research: tool poisoning (MCP03:2025), rug pulls (definitions changed post-approval), tool shadowing, parameter-level poisoning in `inputSchema` | Tool poisoning, supply-chain compromise (ASI02/ASI04) | **Critical safeguard** |
| **Least-privilege agent identities** — agent never inherits the user's full credentials; unique short-lived per-tool/per-task tokens; no shared service accounts. One injection = the blast radius of the broadest credential | Identity & privilege abuse (ASI03); excessive agency (LLM03:2026) | **Critical safeguard** |
| **Human approval for consequential/irreversible ops** — payments, deletion, external comms, prod deploys; approval UI must show *full* tool info (truncation widens the human-model visibility gap). The MCP spec only "SHOULD" require human-in-the-loop — "that word is doing too much work" | Trust exploitation (ASI09); unintended destructive actions | **Critical** for payments/deletion/prod; **recommended** otherwise |
| **Secret isolation from model context** — secrets in a store the model cannot read; injected at tool-execution time, never into context; redacted from logs/traces; avoid aggregating many systems' creds in one server | Exfiltration via injection (LLM02); credential aggregation | **Critical safeguard** (**Inferred** from threat model; corroborated pattern) |
| **Output validation** — schema + allowlist + size validation on model output at every tool/DB/API boundary; treat model output as untrusted input | Improper output handling (LLM05:2026) | **Recommended** → critical where output triggers state changes |
| **Audit logging of agent activity** — tool calls, parameters (redacted), approvals, grants, prompt/response pairs; JSON-RPC MCP traffic evades traditional SIEM patterns — plan reconstruction explicitly | Detection & forensics | **Recommended** → **legal obligation** for EU high-risk AI (Art. 12 logging) |
| **Agent budgets, retry limits, circuit breakers, rollback** — per-task/per-session token, cost, and time budgets with hard caps; kill-switch; defined safe failure modes | Unbounded consumption / "denial of wallet" (LLM06:2026); cascading failures (ASI08) | **Recommended** → critical for cost-exposed or destructive-capable agents |
| **Authenticated inter-agent communication** — mTLS + message signing; no unauthenticated A2A delegation | Message forging between agents (ASI07) | **Risk-dependent** (multi-agent systems only) |

**How controls escalate with capability (Inferred synthesis):** text-only → untrusted-content handling + output validation. Add read tools → read-scoped identities + secret isolation + memory-poisoning defenses. Add write/exec tools → full stack (sandboxing, allowlists, approvals, audit, budgets, rollback). Add payments/production infra → mandatory/dual-control approval, hard spend caps, immutable audit trail, incident runbook. Multi-agent → inter-agent auth + circuit breakers + quarantine.

**MCP-specific warnings worth carrying (Corroborated):** tool descriptions load into agent context at session init and models cannot reliably distinguish operational intent from embedded adversarial instruction (Invariant Labs, Apr 2025); the MCPTox benchmark found most agents vulnerable, with more capable models *more* vulnerable; CVE-2025-49596 (CVSS 9.4) enabled RCE via unauthenticated MCP Inspector instances; the first malicious MCP packages hit public registries in Sep 2025.

**Cross-reference:** the Klarna two-act case (§12) shows what happens when the human-fallback layer is designed as headcount instead of as architecture — the escalation capacity the approval control needs is the same capacity the staffing decision removed.

## 6. Privacy & legal

**Standing caveat (Corroborated):** a privacy-policy page is **not** a substitute for compliance — it satisfies none of consent, minimisation, retention, rights-fulfilment, or security obligations, and an inaccurate policy creates FTC §5 deceptive-practice exposure.

| Control | §25 class | The essential detail |
|---|---|---|
| **Breach notification within statutory windows** | **Legal obligation** (in specified contexts) | GDPR Art. 33/34 — authority within **72 hours**, subjects when high risk (fines up to €20M or 4% turnover — **Verified**). India DPDP — Board without delay + detailed report within 72h; **CERT-In within 6 hours** (live, independent duty). Requires detection → scoping capability: logging that answers *whose data, what data, when* |
| **Honoring deletion / access / correction requests (incl. third-party-sourced data)** | **Legal obligation** (in specified contexts) | GDPR Chapter III; CCPA as amended — **SB 923** (signed 27 Sept 2026, effective 1 Jan 2027) expands deletion from data collected "from" the consumer to "from or about" — broker/enrichment/partner data must be deleted too; online-only businesses must offer a webform intake, not just email. ~20 US state laws in effect; DPDP rights enforceable 13 May 2027. 2026: coordinated state-AG sweeps active; universal opt-out (GPC) signals effectively mandatory across a large bloc of states |
| **Children's-data safeguards** | **Legal obligation** where applicable | COPPA (under-13); DPDP verifiable parental consent + no tracking; California 2027 age-appropriate design law — high-default privacy, data-minimisation, no dark patterns, penalties up to $5,000/$15,000 per violation per child (**Corroborated**) |
| **Data minimisation; retention schedules; purpose limitation** | **Legal obligation** in GDPR/DPDP/CA-children's contexts; **recommended** elsewhere | Collect only purpose-necessary data — audit telemetry, logs, and third-party SDK payloads; scheduled purges; suppression lists where permitted |
| **Consent where required** | **Legal obligation** in specified contexts | Opt-in for sensitive data (growing US consensus); plain-language itemised notices; withdrawal as easy as giving |
| **Third-party sharing inventory; processor contracts** | **Legal obligation** (processor contracts: GDPR Art. 28, DPDP; sharing/opt-out duties: state laws — pixels/SDKs count as "sharing"/"sale") | Data map of all third-party transfers; DPAs with processors; honor universal opt-out signals where required |
| **Posting a privacy policy as the compliance measure** | Anti-pattern — explicitly **not** a control | (**Corroborated**) |

**AI-specific legal duties (Corroborated):** EU AI Act in force 1 Aug 2024 — Art. 50 transparency duties (disclose AI interaction, machine-mark synthetic content; effective 2 Aug 2026; fines up to €15M or 3%) and Art. 15 cybersecurity/robustness for high-risk AI (adversarial resilience demonstrated through documentation and testing; deadlines 2 Dec 2027 / 2 Aug 2028 per the May 2026 Digital Omnibus). EU Cyber Resilience Act: products with digital elements in scope; vulnerability-reporting duties from Sept 2026; full conformity Dec 2027. NIS2: in-scope entities must include AI systems in risk management and incident response.

**Liability for AI statements — cross-reference to §12:** *Moffatt v. Air Canada* (2024 BCCRT 149 — **Verified**) established that a support bot's statements carry the company's legal authority; the "chatbot as a separate legal entity" defense was rejected as "a remarkable submission." No disclaimer separates the two.

## 7. How to read this index (the meta-rule)

From §25-F3: **turning this index into a universal mandate is itself potentially harmful when misapplied.** Every class above is context-sensitive. Universal mandates produce waste (CSRF tokens on bearer-token APIs), new vulnerabilities (hard lockout as a DoS button; security questions as a weak credential), or false assurance (flagging public keys while RLS is off; a policy page as "compliance"). The research's recurring formulation: *make unauthenticated endpoints an explicit reviewed decision, not an oversight* — and equally, make *applied* controls explicit reviewed decisions, not cargo cult.
